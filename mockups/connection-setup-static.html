Requirements by connection type

Same computer

Windows host from WSL

  1. Run WSL with Windows interoperability and drive mounting available.
  2. Detect the signed-in Windows profile and translate its paths using WSL.
  3. Read Windows agent settings and inspect detected folders.
  4. Enable sync for the desired providers.

If detection fails: show “Windows profile unavailable” and explain whether Windows command access or the mounted drive is missing. Allow an explicit mounted folder mapping.

Same computer

Another WSL distribution

  1. Choose an installed distribution visible to wsl.exe.
  2. Start it explicitly if stopped.
  3. Ensure python3 is available to the distribution’s default user.
  4. Check that user’s provider folders, then enable sync.

No SSH or Tailscale required. Discovery must not start stopped distributions. A stopped distribution shows “Start distribution,” not an authentication error.

Another computer

SSH over Tailscale

  1. Connect both computers to the tailnet. Permit the SSH port through tailnet access rules and the destination firewall.
  2. Enable an SSH server on the destination. On macOS: System Settings → General → Sharing → Remote Login; allow the intended account.
  3. Set up SSH trust and unattended authentication from the environment running HarnessKit.
  4. Check python3 and read/write access to the chosen folders.
  5. Test, review inventory and direction, then enable sync.

This is ordinary SSH carried over Tailscale. The separate Tailscale SSH feature has platform and policy requirements; do not assume that installing Tailscale enables it.

Another computer

Direct SSH · LAN / VPN / alias

  1. Enter a reachable hostname, IP or SSH alias, account and port.
  2. Enable the destination’s SSH service and allow that port through its firewall.
  3. Verify the host fingerprint and configure unattended key authentication.
  4. Check Python 3 and access to the provider folders.
  5. Test, review inventory and direction, then enable sync.

Tailscale is optional. SSH aliases and agents must be available to HarnessKit’s account and process. Current remote execution expects a Unix-like shell and Python 3; native Windows SSH is not yet supported by this helper.

Already accessible storage

Local or mounted folder

  1. Mount the disk or network share in the environment running HarnessKit.
  2. Select an absolute provider skills directory.
  3. Check that the mount is present and readable; writing requires permission to replace files and directories.
  4. Review the environment identity and sync policy, then enable sync.

HarnessKit does not establish SMB/NFS mounts or manage their credentials. An unavailable mount must remain unavailable; it must not be treated as an intentional deletion.

Say what failed, and what to do next

Connection refused → Start Remote Login / SSH service and check the port.

Connection timed out → Check power, network route, tailnet access and firewall.

Host key not trusted → Verify the fingerprint using the SSH client in the HarnessKit environment.

Authentication failed → Check the account, authorized public key and SSH agent.

Python 3 unavailable → Install Python 3 for that destination account.

Folder unavailable → Correct the path, mount or account permissions.

Sleep prevention can keep a machine reachable; it does not enable SSH or configure authentication. Automatic sync also requires HarnessKit to keep running.
